PerguntaResposta na CredSim (estado de fábrica)
✕Há autorização e rate limit por usuário? (LLM01, LLM10)Não. Sem defesa ligada, qualquer identidade autodeclarada chama qualquer endpoint sem limite.
✕O system prompt guarda segredo, ou a segurança depende dele ser secreto? (LLM07)Sim — o Chat carrega um código de aprovação interno direto no texto do system prompt.
△A proveniência do modelo foi verificada? (LLM03)Parcial — modo real usa a API oficial da Anthropic (proveniência garantida pelo provedor); modo local roda qualquer modelo que alguém baixe no Ollama, sem verificação nenhuma.

Checklist de saída e execução

PerguntaResposta na CredSim (estado de fábrica)
✕A saída é tratada como não confiável e sanitizada antes de renderizar/executar? (LLM05)Não — HTML do Chat não é escapado; código SQL/Python do Agente de análise executa sem validação.
✕Ferramentas de alto impacto têm menor privilégio e exigem revisão humana? (LLM06)Não por padrão — mas o mecanismo "propõe → humano confirma" já existe no código para e-mail e transferência; só precisa ser ligado.
✕Há isolamento de tenant no RAG? (LLM08)Não — a busca da Central de Políticas ignora o dono do documento por padrão.

Checklist de monitoramento

PerguntaResposta na CredSim
✓Há logs para investigar um incidente?Sim — todo evento passa por logging_util.py (sem persistência em disco: cai a zero a cada restart).
△Há detecção de anomalias (volume, padrões de injeção, respostas fora do perfil)?Básica — cada evento já chega marcado com uma anomalia se bater num padrão conhecido (segredo vazado, comando sem validação, custo fora do padrão). Não é detecção estatística de produção.
✕Há red-teaming periódico?Não existe processo formal — é um gap organizacional, não técnico: nenhuma linha de código resolveria isso sozinha.

A matriz que amarra o curso: componente × risco × controle

Cada linha cruza um componente (Passo 1), um risco OWASP 2025 (Passo 2) e o controle de defesa em profundidade que deveria cobri-lo (Aula 5). Uma célula vazia — controle que não existe, ou existe mas tem um jeito de contornar — é um achado, documentado no Passo 4.

ComponenteRisco principalControle esperadoCobertura hoje
Chat de solicitaçãoLLM01 + LLM07input_validation + output_validationExistem — mas juntos não cobrem 100%: o ataque reescrito ainda passa pela entrada.
Validação de documentoLLM01 indireto + LLM06input_validationExiste e cobre — trata o conteúdo do documento como dado, não instrução.
Central de Políticas (RAG)LLM08 + LLM02input_validation (isola tenant) + output_validation (ignora instrução obedecida)Existem, dois controles independentes — só falha se nenhum dos dois estiver ligado.
SuporteLLM02api_securityExiste — mas admin1 contorna mesmo com o controle ligado.
Agente de análiseLLM05 + LLM06output_validationExiste e cobre UPDATE, DELETE e DROP igualmente.
Multi-agent (Negociação)LLM06 propagado + LLM03least_privilegeParcialmente vazia — cobre a aprovação automática do desconto, mas nenhum controle impede o e-mail de sair para o fornecedor.
Aprovação / LiberaçãoLLM06least_privilegeExiste e cobre os dois agentes (e-mail e transferência).
Controle de acesso / API expostaLLM02 + LLM10api_securityVazia para admin1 — nenhum toggle cobre um bypass fixo no código; para o resto (IDOR comum, rate limit) o controle existe e cobre.
Exemplo do método (do slide da aula) O exemplo clássico deste passo é a API sem rate limit: pergunta-se "há limite por usuário?", a resposta é não, e a célula vazia já nasce achado — impacto médio × probabilidade alta. Aqui encontramos mais dois gaps do mesmo tipo: o e-mail que sai sem controle na Negociação, e o bypass da identidade admin1, que nenhum toggle de defesa cobre porque não é uma lacuna de configuração — é uma porta lateral no desenho do controle de acesso.
